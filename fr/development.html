Development

Environment setup

Requires Python 3.14 and uv.

cp .env.example .env          # fill in tokens/credentials, see below
make install                  # uv sync --group dev --group docs
make dev                      # uv run uvicorn api.main:app --reload --port 3002
make test                     # uv run pytest (with coverage)
make check                    # lint + typecheck + test
make docs                     # this Sphinx site -> docs/_build/html/index.html

Or the equivalent uv run ... commands directly – make is a thin wrapper (see the Makefile), not a requirement. Day to day:

uv run ruff check api tests
uv run ruff format
uv run mypy api
APP_TOKEN=t uv run pytest -q --no-cov -p no:cacheprovider
uv run --group docs sphinx-build -W -q docs /tmp/docs   # what CI checks

To run the full stack (API, Celery worker and beat, Redis, OCR sidecar) in Docker instead: docker compose up -d --build (see Operations).

Airtable

AIRTABLE_BASE_ID in .env selects the base: production, or the dev base copied from it (the one scripts/reset_dev_store is allowed to touch, paired with the RewakeDev Shopify store below). Get a personal access token with read/write access to that base (plus schema.bases:read), then verify it:

make airtable-check
# or: uv run python -m scripts.airtable.check_credentials

uv run pytest genuinely calls Airtable for a few older tests (tests/test_auth.py, tests/test_airtable.py, tests/test_contact_*.py) – they have no mock/fixture layer yet (the newer catalog, script and AI tests use in-memory fakes). That’s exactly why tests don’t run in CI (see Operations): they need six working token/credential secrets (ADMIN_TOKEN, HELLOPRO_TOKEN, MACHINIO_TOKEN, APP_TOKEN, AIRTABLE_TOKEN, AIRTABLE_BASE_ID) just to pass, and a scope/typo issue in any one of them produces a wall of unrelated-looking 500s rather than a clear failure – more fragile than valuable as a required gate today. Run them locally with a real .env instead.

Shopify (dev store)

The Shopify scripts (shopify_catalog_reconciliation, create_product_shopify, update_product – see Scripts) and the scripts/shopify tools call Shopify via SHOPIFY_SHOP_DOMAIN/ SHOPIFY_CLIENT_ID/SHOPIFY_CLIENT_SECRET/SHOPIFY_API_VERSION in .env.example (required scopes: read_products, write_products, write_inventory, read_files, write_files). Test it against the RewakeDev Shopify development store, never production (rewake-2).

There is no access token to configure: Shopify’s client-credentials tokens live ~24h (a lifetime Shopify fixes), so api/integrations/shopify_auth.py exchanges the client ID/secret at runtime, caches the token in Redis for the API and every worker, renews it 10 minutes before expiry, and on a 401 renews it and retries once. The client ID/secret themselves don’t expire. To verify the credentials and the granted scopes:

make shopify-check    # uv run python -m scripts.shopify.check_credentials

Client credentials only work for a store in the Dev Dashboard app’s own organization. A new scope only reaches the token after the app version declaring it is released and the update approved on the store. To start the dev store over, make reset-dev-store empties it (and the dev base’s Annonces Shopify) behind a hardcoded guard that refuses any other store/base; create_product_shopify then recreates the listings. Point this project’s .env at that store when testing anything Shopify-related here.

Development scripts

scripts/ (repository root, not part of the api package) holds operator tooling, run as a module (or through the Makefile):

uv run python -m scripts.airtable.check_credentials   # make airtable-check
uv run python -m scripts.shopify.check_credentials    # make shopify-check
uv run python -m scripts.reset_dev_store              # make reset-dev-store
uv run python -m scripts.shopify.update_warranty_text # make update-warranty-text

plus scripts/release/release_notes.py (run by CI) and scripts/deploy/deploy.sh (run on the server, see Operations). See scripts/README.md for what each one does.

Known gaps this tooling surfaces

Adding ruff/mypy/coverage/CI to a codebase that had none of it before makes existing debt visible; none of the following was introduced by adding the tooling itself, and none of it was fixed as part of adding it (fixing business logic wasn’t in scope for that pass):

  • 2 tests marked ``xfail`` (tests/test_fees.py::test_distritec_fees_simple_package, test_distritec_fees_multiple_packages, both strict=True): the expected totals don’t match api/services/fees.py’s current output. Needs someone who knows the intended Distritec tariff to say which side is wrong. strict=True means if the underlying bug ever gets fixed, these flip to a hard test failure (XPASS) instead of silently staying green – remove the marker at that point, don’t leave it in place.

  • mypy: clean at its current (non-strict) level – the ~32 findings this surfaced when first turned on (mostly a dict[str, str] parameter annotation that was actually dict[str, Any] in practice, since Airtable fields aren’t all strings, plus a few missing local annotations and two untyped tariff-table dicts in api/services/fees.py) have all been fixed. --strict finds ~106 more, almost all missing-annotation noise across the wider codebase rather than bugs – a deliberate future ratchet, not turned on yet.
