Update Product

Module

api.scripts.update_product

Schedule

on-demand only (schedule = None) – requires exactly one of record_id (a Variation) or model_id (a Model)

Reads

Airtable

Writes

Shopify – the other script here that writes anything, alongside create_product_shopify (which creates a brand-new listing; this one only ever updates one that already exists, or deletes it when to_sell_on_shopify is “Non”) – and deletes the “Annonces Shopify” record in that case

Origin

ported in-process from a sibling project (Update-Product, a separate git repository) that this script previously shelled out to as a subprocess – see “Deliberate deviations” below

What it does

Syncs an existing Shopify product from Airtable. Airtable is the source of truth for everything it writes:

  • Product: title (Name), description (Short description), vendor (Marque, or Sans marque), product type (the Type’s Name), and status (the linked “Annonces Shopify” record’s Status: active/draft/archived; left as is when empty, a failure when it’s anything else).

  • Metafields: the same set create_product_shopify writes – long_description, reconditionnement, livraison, garantie, main_table – plus the family “filter” metafields (FAMILY_FILTER_METAFIELDS, currently only Balances). A filter spec Airtable doesn’t have is listed in details.filter_specs_missing (no alert email – this script runs on every stock change).

  • Images: the Model’s Photo neuve, then the Photos marketplace of its first sellable unit that has any – the same images create_product_shopify uploads (see “Images” below).

  • Documentation PDF: see below.

  • Options and variants: the product is reconciled to Airtable, never just patched. Options: “État esthétique”, plus the size option (the Variation’s Variant_value; label from the Type, see _variant_option_name) whenever any of the Model’s Variations has a Variant_value – with or without stock right now, since that’s what reconciliation matches a variant against. Variants: exactly one per sellable (condition[, variant value]) combination, with Airtable’s price, weight and stock – a missing one is created, one with nothing left to sell is deleted. When the options change (e.g. a product created without the size option), every variant is recreated under the new options. Shopify requires at least one variant, so when the whole Model has nothing left to sell, the existing variants are kept and set to a zero stock.

When the Model’s to_sell_on_shopify is “Non”, the run instead deletes the Shopify product and its “Annonces Shopify” record (every linked one). A product already gone from Shopify (404) still has its listing deleted; any other Shopify error stops before the listing is deleted, so a retry still knows what to delete. An empty to_sell_on_shopify is a failure – deleting a live product over an unfilled field would be too destructive a guess.

Two entry modes, both real (nothing here previews or dry-runs):

  • record_id (a Variation id, the default/existing convention): resolves that Variation’s parent Model, then updates the whole product. Shopify variants all belong to one product per Model anyway, so “update one variation” and “update its model” converge on the same write.

  • model_id: the identical pipeline, entered directly from a Model id – what the Airtable automations use (see “Triggering from Airtable”).

Nothing here creates a brand-new Shopify listing – see create_product_shopify for that. A Model with no Shopify product yet (Aucun produit Shopify associé à ce modèle) is a validation failure here, not something this script will fix.

Triggering from Airtable

The four automations that used to call the queue manager (“Update fiche shopify (vendus)”, “(Pas a vendre)”, “(modifs)”, “Update quantité shopify (entry)”) all run the same script (“Run script” action, input model_id = the Model’s record id), with AIRTABLE_AUTOMATION_TOKEN:

let inputConfig = input.config();

const API_URL = "https://api.rewake.fr/internal/scripts/update_product/run";
const API_TOKEN = "<AIRTABLE_AUTOMATION_TOKEN>";

let model_id = Array.isArray(inputConfig.model_id) ? inputConfig.model_id[0] : inputConfig.model_id;
if (!model_id) throw new Error("Model ID manquant");

let response = await fetch(`${API_URL}?model_id=${encodeURIComponent(model_id)}`, {
    method: "POST",
    headers: { Authorization: `Bearer ${API_TOKEN}` }
});
if (!response.ok) throw new Error(`Erreur API: ${response.status} - ${await response.text()}`);

let result = await response.json();
console.log("✅ Tâche ajoutée:", result.task_id, result.status);

The response only confirms the run was queued; its outcome is in GET /internal/scripts/update_product/runs (and the alert email on failure).

Images

  • Source: the Model’s Photo neuve (all of them; missing, or any under 300x300px, is a failure), then the Photos marketplace of the first sellable unit that has any (under 300x300px or duplicating a Photo neuve url: skipped) – shared with create_product_shopify via _marketplace_photo_attachments.

  • Change detection: the Airtable attachment ids the Shopify images came from are recorded, in order, in the custom.images_airtable_ids metafield. Images are replaced only when that differs from Airtable’s current list, or when Shopify’s image count no longer matches. A product whose images predate this (no recorded ids) has them replaced once.

  • Replacement: new images are uploaded first (in order, with their position); the old ones are deleted only once every upload worked. A failed upload deletes what it added and leaves the old images in place.

  • Worth knowing: the marketplace photos follow the first sellable unit – when that unit is sold, the next one’s photos replace them on the next update.

Documentation PDF

Shared with create_product_shopify via api/scripts/_product_documentation.py (upload through api/integrations/shopify_files.py, GraphQL).

  • Source: the Model’s Airtable Documentation attachment field – the first attachment that is a PDF (MIME type, or a .pdf filename). Other attachments are ignored.

  • Target: the product metafield SHOPIFY_PDF_METAFIELD_NAMESPACE.SHOPIFY_PDF_METAFIELD_KEY (default custom.pdf_descriptif, the “PDF Descriptif” definition), type file_reference, plus a companion single_line_text_field (custom.pdf_descriptif_airtable_id by default) recording the Airtable attachment id the Shopify file came from.

  • Upload: the PDF is downloaded from Airtable (signed url, fetched fresh with the record) and sent through Shopify’s staged upload -> fileCreate -> poll until READY -> metafieldsSet (both metafields in one atomic call).

  • Change detection: same “diff against live Shopify” approach as the rest of update_product – no extra state store. Upload when Shopify has no PDF, or when the recorded source id differs from Airtable’s current attachment id (Airtable gives a replaced file a new id). A Shopify PDF set by hand before this sync existed has no source id, so it is replaced once by Airtable’s, then stays stable.

  • Never clears: an empty Airtable field writes nothing (documentation_status: "absent") – there’s no deletion-sync convention in this project.

  • The replaced Shopify file is not deleted from the Files library (it may be referenced elsewhere).

  • Scopes: the Shopify app needs write_files and read_files (confirmed missing on the RewakeDev token on 2026-09-28 – fileCreate answers ACCESS_DENIED without them).

  • Failure handling: runs inside the per-Model lock, after variants. A failed upload doesn’t stop the rest of the sync, but turns the run into a failure afterwards (same rule as a failed variant creation: it’s what reconciliation’s documentation bulk action runs this script for).

Locking: runs for one Model never overlap, and never get dropped

  1. The per-record_id Redis lock in api/tasks.py (shared by every script) guards the outer request layer – keyed by whatever the caller passed in as record_id. update_product sets requeue_when_locked, so a run that finds it held is put back on the queue instead of being skipped.

  2. A second lock, acquired inside run() once the Model is resolved, keyed by the Model id (RunStore.acquire_lock("update_product_model", model_id)) – the one that actually matters, since a Variation id and a Model id (or two Variations of one Model) resolve to the same Shopify product. A run that finds it held raises RequeueLater, and api/tasks.py puts it back on the queue (5s countdown, up to REQUEUE_MAX_RETRIES = 120 times, then a failure run is recorded).

Every Airtable read happens after the Model lock is acquired, with a fresh cache – a run that waited its turn syncs Airtable’s latest state, not what it saw when it was triggered. A waiting run isn’t recorded in the run history; only the run that actually happens is.

How it works

  1. Resolve the Model: record_id mode verifies the id really belongs to the Variation table (Airtable’s single-record GET doesn’t validate that – see _assert_belongs_to_table), then reads its Model link field; model_id mode verifies the id belongs to Model directly.

  2. Acquire the per-Model lock (or requeue – see above), then read the Model.

  3. to_sell_on_shopify = “Non”: delete the Shopify product(s) and listing(s), done.

  4. Validate: a Shopify product is linked (via Annonces Shopify -> ID_shopify, the same _resolve_listing_ids helper create_product_shopify.py uses), the listing’s Status is valid, the Type exists, the weight is a number. Collect the sellable units with create_product_shopify.py’s own _collect_sellable_units/ _build_variant_rows (so both scripts agree on what the variants should be) – an empty result is fine here: it means zero stock everywhere.

  5. Fetch the live product, then sync, in this order: variants (stock first – it’s what matters most if anything later fails), product fields, metafields, documentation PDF, images. Each step diffs against the live product first – a no-op write is never sent. Variants go through one product PUT with the full variant list (Shopify REST: a listed variant with an id is kept and updated, one without is created, an unlisted one is deleted) – which is also what lets the options themselves change – then each variant’s stock is pushed. A variant’s identity is its option values, stripped, in position order.

  6. A failure in any step is collected, not fatal: every other step still runs, then the run reports status="failure" with every reason (first 5 in details.error) and the partial progress. A missing/invalid Photo neuve works the same way: images are skipped, everything else syncs, the run fails.

Deliberate deviations from the source (Update-Product)

  • Queued, not skipped, when busy. An earlier version of this port skipped a run that found the product’s lock held (status="skipped") – but that run could be the one carrying the newer Airtable data (a sale triggering two automations at once), so it now waits its turn instead.

  • In-process, no subprocess. The source shelled out to uv run Update-Product/main.py <record_id>, parsing captured stdout/stderr to guess success (stderr == "") – unreliable, since Update-Product logs structured JSON events to stderr by design, even on a clean run. This port sidesteps that signal entirely.

  • No sandbox/dry-run mode. The source defaulted to a sandbox mode (reads real data, logs what it would do, never actually writes) unless an ENVIRONMENT/ENV var said “prod”. This port always writes for real once triggered, matching create_product_shopify’s own behavior and this codebase’s existing posture.

  • No ALLOW_VARIANT_CREATE permission gate. The source required an explicit opt-in env var before it would create a missing variant, defaulting to blocking that. This port always creates a missing variant – a routine, expected part of “update”, not an edge case to guard against (this is also exactly what makes reconciliation’s “Variations absentes de Shopify” -> “Mettre à jour” button meaningful).

  • REST, not GraphQL, for every Shopify write. The source used Shopify’s GraphQL Admin API (productUpdate, metafieldsSet, productVariantsBulkUpdate, productVariantsBulkCreate) plus one REST inventory call. This port extends the existing REST-only ShopifyAdmin (api/integrations/shopify_rest.py) instead of introducing a second, GraphQL-based client alongside it – one consistent Shopify integration style for both scripts, same asymmetric retry semantics (see that module’s own docstring), same positional option/variant matching create_product_shopify.py’s own _create_variants already established.

  • Inventory location: the existing SHOPIFY_LOCATION_ID constant, not a live lookup. The source queried Shopify for “the first location” on every run (locations(first: 1)) and used whatever came back. This port reuses the already-configured SHOPIFY_LOCATION_ID (set up for create_product_shopify) – the dev store alone has 3 locations, so “whichever one Shopify lists first” is a real correctness risk the source carried, not something worth preserving.

  • A single _ValidationFailed exception, not the source’s 9-class hierarchy. Update-Product/errors.py’s granular exceptions (RecordNotInVariationTableError, NoUnitsLinkedError, NoPriceError, etc.) map 1:1 to specific checks, but create_product_shopify.py already established a single internal exception (message + extra_details for Airtable links) as this codebase’s own convention for exactly this kind of “one of several checks failed” flow. This port follows that precedent rather than introducing a second error-handling philosophy alongside it – each check still raises a distinct, specific message, just not a distinct class.

  • Alerts via the existing Gmail API service, not raw SMTP. The source sent alert emails via smtplib and a Gmail app password (SMTP_GMAIL_PASSWORD) – the same category of credential exposure flagged in Update-Product/docs/incident-2026-08-shopify-duplicates.md’s security remediation checklist. This port reuses api/services/gmail.py’s send_alert_email (Gmail API + a service account), exactly like create_product_shopify.py already does.

  • This port is the incident doc’s own target architecture. That document’s “architecture cible” diagram explicitly names bringing this logic in-process behind an authenticated internal endpoint, with a per-Shopify-id lock and no silent-success masking of a real failure – this is that migration, not an unrelated refactor.

Known risks / things worth reviewing

  • A model_id-mode (or a Model’s other Variations’) update isn’t attributed back to an individual Variation in reconciliation’s cross-reference. attach_update_attempts in shopify_catalog_reconciliation.py only matches a stored update_product run against variations_missing_in_shopify via that run’s own record_id – a run triggered by model_id (or by a different sibling Variation of the same Model) has no record_id of its own to match on, so it won’t show up as “already tried” against a Variation it may well have actually updated.

  • Fixed: a product created without the size option could never get it. Confirmed live (dev store, “RT PCR Thermo Scientific QuantStudio 5”): create_product_shopify only added the size option when more than one size had stock at creation, and update_product read the option count from the live product, so its “0.1 mL / Très bon” row matched the existing condition-only “Très bon” variant and every run reported success without changing anything – while reconciliation kept listing “0.1 mL” as missing. Both scripts now decide the options from Airtable (_model_has_variant_values), and update restructures a product whose options differ. Worth knowing: a product whose option names differ from what Airtable implies (e.g. renamed by hand) has all its variants recreated once.

  • No dedicated test against a live Shopify product with a genuinely different historical option-1 value. The positional variant-matching assumes option 1 is always literally “État esthétique” (fixed at creation time) – true for everything create_product_shopify.py has created, but not verified against an older, differently-structured product that might predate that convention.

  • ~~First real end-to-end verification against the dev store is still pending~~ – done: both entry modes and the reconciliation buttons were run live against the dev store, which is exactly what caught the bug below.

  • Fixed, but worth knowing about: variant option values must be compared stripped, not raw. Confirmed live: Airtable’s Variant_value can carry incidental trailing whitespace ("120x47 ") that Shopify itself trims on save ("120x47"). Comparing the raw, untrimmed Airtable value against Shopify’s own (already-trimmed) option values meant an already-existing variant was never recognized as a match – update_product would then attempt to create a duplicate variant with the same option combination, which Shopify correctly rejects, and (before this fix) that rejection was silently logged and swallowed, with the run still reporting status="success". Both bugs are now fixed: _variant_key_from_row/ _variant_key_from_shopify strip both sides before comparing, and a failed variant creation now makes the whole run report status="failure" (with the real Shopify rejection reason in details.error) instead of silently succeeding. Since then, every variant sync failure (price, weight, stock, zero stock) does the same.

  • A requests.Response is falsy for any non-2xx status (Response.__bool__ returns self.ok) – code that checks if response else None instead of if response is not None else None silently discards the real status code/body of a genuine error response. This exact mistake is what hid the bug above during initial testing (logs showed "status": null for a real 422). Fixed via _response_error_detail, which checks is not None and includes the actual response body. Worth grepping for this same if response else ... pattern if it’s ever copied elsewhere.

Metrics and details

GET /internal/scripts/update_product/runs returns, per run:

Key

Meaning

metrics.variants_created

How many Shopify variants were newly created this run

metrics.prices_updated / metrics.weights_updated / metrics.quantities_updated

How many existing variants had their price/weight/inventory changed

metrics.variants_deleted

How many Shopify variants with nothing left to sell were deleted

metrics.options_updated

1 when the product’s options were changed (variants then all recreated)

metrics.quantities_zeroed

How many variants were set to a zero stock because the whole Model has nothing left to sell

metrics.metafields_updated

How many metafields were actually written (0 if all already matched)

metrics.images_uploaded

How many images were uploaded this run (0 when unchanged)

metrics.documentation_updated

1 when a documentation PDF was uploaded this run, else 0

details.action

updated, or removed (to_sell_on_shopify = “Non”)

details.deleted_shopify_product_ids / details.deleted_listing_record_ids

What a removed run deleted

details.product_fields_updated

Which of title/body_html/vendor/product_type/status were written

details.description_updated

Whether body_html was among them

details.images_status

uploaded / unchanged / failed / skipped (no valid Photo neuve)

details.filter_specs_missing

Family filter specs Airtable doesn’t have (only when some are missing)

details.documentation_status

uploaded / unchanged / absent (no PDF in Airtable, Shopify untouched) / failed

details.model_id

The Model this run resolved to, regardless of entry mode

details.record_id

The Variation id, only when that was the entry mode used (absent for model_id mode)

details.title

The Model’s name, present on every outcome

details.shopify_product_id / details.shopify_product_url / details.airtable_listing_url

Links to the product this run was about

details.error

Present on failure

details.airtable_model_url / details.airtable_variation_url / details.airtable_unit_url

Best-effort links to the Airtable record a validation failure is actually about – same convention as create_product_shopify

Where to look

  • Trigger/history: POST /internal/scripts/update_product/run?record_id=recXXX (or ?model_id=recXXX), GET /internal/scripts/status/{task_id}, GET /internal/scripts/update_product/runs, GET /internal/scripts/update_product/current (live stage while running).

  • Logs: structlog, logger api.scripts.update_product (business logic) and api.tasks (task lifecycle).

  • Source: api/scripts/update_product.py; shared helpers with create_product_shopify.py (the exception class, the Airtable cache, link builders, unit/spec aggregation) live in api/scripts/_shopify_links.py.

  • Tests: tests/test_update_product.py.
